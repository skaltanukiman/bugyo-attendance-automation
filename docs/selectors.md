# 実画面へのセレクタ設定

`src/browser/attendancePage.ts` にDOMの構造やCSSクラスを埋め込まず、`config/selectors.json` に分離しています。未設定の要素があるか `verified: false` の間は通常の自動入力・保存に進みません。`check-screen.bat` は未確認設定でも読取だけを行えます。利用者が指示した通しテストは `test-run.bat`（`--trial`）で実行します。未確認設定での入力・保存をその実行の間だけ許可し、設定構造・年月・競合・保存内容の検証と最終申請の禁止は維持します。以下は実画面確認担当者向けの手順です。

## 確認する情報

1. 表示中の勤務実績申請タイトルと下書き保存ボタンで対象ページを識別します。非表示の同名タイトルは除外し、表示中のタイトルが複数ある場合は停止します。タイトルは入力対象ではありません。対象iframeの有無も確認します。識別時は各タブのタイトル総数・表示中の数・下書き保存ボタン数・日付行数・iframe数を出力し、候補0件と複数件を別のエラーとして扱います。URLやHTMLは診断ログに出力しません。
2. 日付行の親要素と日付セルを確認します。今回の画面には年月表示がないため、`periodSource: rowDates` と `period: null` を設定し、`dateEvidence` の属性から対象年月を取得します。全日付の年月・日付表示・重複・欠落を確認します。表示要素がある別画面では従来の `display` 方式も使えます。
3. 各行の勤務体系・事由・出退勤・休憩・実働を読み取る要素。`readMode: text` はセル本文、`value` はinput/selectの現在値、`attribute` は `readAttribute` で指定した属性を読みます。`emptyAttributes` が指定されている場合、すべて空文字であることを確認します。複数の事由を単一事由として上書きしません。
4. 入力欄と操作方式。ネイティブinputは `fill`、ネイティブselectは `select`。値は勤務体系・事由のコード、時刻は`09:00`、休憩は小数時間`1.00`です。selectのoption値がコードと一致することを確認してください。
5. 編集ダイアログがある場合は行内の `editButton`、画面内の `editor`、編集画面内の `applyButton` をすべて設定します。直接編集ならすべて `null`。行確定ボタンはsubmitではなく、最終申請に無関係なものであることを確認してください。
6. 今回は成功メッセージが出ず、申請期間画面へ戻ります。既存下書きの更新では件数が変わらない可能性があるため、`saveMode: reopenDraft` として保存後に下書きを開き直して照合します。遷移先の目印を `returnMarker`、一覧への入口と一覧内の要素を `draftList` に設定します。一覧の1行と詳細表示からの「申請書入力」ボタンの実DOMは提供済みです。

保存ボタンは変更可能な自由セレクタではなく、role=button、正確な名前「下書き保存」で固定します。最終「申請」のセレクタや操作メソッドはありません。クリック共通ガードは通常「申請」を含む名前・タイトル・本文を拒否します。下書き確認の専用操作では、完全一致する「勤務実績申請」のリンクと「申請書入力」の非送信ボタンだけを許可します。名前・タイトル・aria-labelなどに他の文字が含まれる場合も拒否します。リンクはhrefが空文字または#、移動先タブが未指定または_selfであることを確認します。

## 設定のスコープ

| キー | 検索範囲 |
| --- | --- |
| `frame` | ページ。iframeセレクタ1つ。なければnull |
| `title`, `period`, `rows`, `editor`, `saveSuccess` | ページまたは対象iframe |
| `draftCount`, `returnMarker` | ページまたは対象iframe。遷移後も再検索 |
| `draftList.entry`, `title`, `loaded`, `rows` | ページまたは対象iframe。下書き一覧の入口・タイトル・読込完了・各データ行 |
| `draftList.status`, `name`, `period`, `open` | 一覧内の該当行。状態・申請名・期間・下書きを開く要素 |
| `draftList.openEditor` | ページまたは対象iframe。詳細表示内の「申請書入力」ボタン |
| `dateCell`, `fields.*.read`, `editButton` | 該当する日付行 |
| `dateEvidence.selector` | 日付行内。指定属性の年月日をExcelと照合（チェックボックスは読取のみ） |
| `fields.*.input`, `applyButton` | 編集ダイアログ、または直接編集時の日付行 |
| `fields.*.activate`, `fields.*.commit` | 編集ダイアログ、または日付行。編集開始セルと確定先 |
| `fields.*.commitField` | 確定先が勤務体系または事由の入力欄を開く場合、そのフィールド名。commitと対象フィールドのactivateが一致することを検証 |
| `fields.*.hour`, `minute`, `dayType` | `fields.*.input` の分割入力コンテナ内 |
| custom方式の `option` | ページまたは対象iframe |
| custom方式の `clear` | 編集ダイアログまたは日付行 |

`rows` は全日付行にマッチさせ、`dateCell` を正規表現で照合して日付行を特定します。行番号やクリック座標は使いません。日付行・入力欄の重複や非表示は停止条件です。仮想スクロールで未表示行がDOMにない場合も推測で進めず停止します。必要ならDOM確認後にスクロール用アダプターを追加してください。

customドロップダウンでは `control: "custom"`、コード置換用 `option: "[data-code='{code}']"` のような実際に確認したセレクタ、空欄へ戻す `clear` を設定します。これは形式例であり、奉行にこの属性があるという意味ではありません。

`tests/fixtures/selectors.json` に完成した**模擬画面専用**設定があります。キーの参考としてだけ使用し、実サイトへコピーしないでください。複数iframe階層、候補検索で確定する複雑なUI、保存確認ダイアログなどは実DOM確認後にPage Objectのアダプターを拡張する必要があります。未対応方式をセレクタだけで対応可能とは扱いません。

## 提供HTMLから確認できた構造

日付の固定表と勤務入力の横スクロール表は別々ですが、`tr.js-cm-scrTbl__innerTr` が両方を含みます。同じクラスの非日付行を含めないよう、`rows` は `tr.js-cm-scrTbl__innerTr:has(input[data-labordate])` としています。この親行を日付セルで絞り、`data-labordate` の年月日も照合します。属性の欠落で行が除外されても、月の全日付が揃わなければ停止します。左右の表に同じ行IDがあるため、行ID・行番号に依存しません。実日付や行識別子は設定へ固定していません。絞り込み後の件数と全日付の年月日属性は実画面で確認済みです。

- 勤務体系・事由はセルを選択してコード入力欄を開く形式です。実画面の入力後に、`data-code` / `data-code1` が元の値を保持し、表示や入力欄だけが変わることを確認しました。このため現在のコードは `readMode: text` でセル表示から読みます。編集中のコード欄は、自動処理が開く直前に記録した表示コードと `inputValue()` の一致を確認して読みます。記録がない編集欄や値が変わった編集欄は停止条件です。HTMLのvalue属性や元のdata-code属性を現在値として使いません。記録は日付と項目別にメモリで持ち、下書きを開き直した際には破棄します。
- 出退勤は `splitTime` 方式です。`dayType` は当日1・翌日2、`hour` と `minute` を別々に入力します。例として25:30は翌日・01・30です。前日区分には対応しません。
- 休憩は `splitDecimal` 方式です。提供HTMLの `DecimalSys` に合わせ、1.50時間なら整数部1・小数部50を入力します。入力欄のラベルが「分」でも30へ変換しません。
- 各セルは `activate` で開き、入力後に `commit` の要素をクリックして編集欄が閉じたことを確認します。その後、既存の検証処理で全対象行を読み戻します。時刻・休憩のセルが実行開始前から編集中の場合は、利用者が確定または取り消してから実行してください。

利用者から、事由・出退勤・休憩は日付セルをクリックしても戻らず、別の入力欄をクリックすると元の表示に戻ると確認できました。このため、勤務体系の `commit` は事由セル、その他の項目は勤務体系セルとしています。`commitField` で移動先のコード欄を示し、開く前の表示コードを記録します。移動先のコードは書き換えず、その記録と現在の入力値の一致を読み戻し時に確認します。模擬画面でも、日付クリックでは閉じず、data-code属性は変更前の値を保持する方式にしています。実画面で入力後の表示と、保存済み下書きを開き直した全対象日の値の一致を確認済みです。翌日の時刻を非編集状態でどう表示するかも未確認であり、未知の表示は推測変換せず停止します。

## 下書きを開き直す保存確認

下書き保存を1回だけ押し、申請期間の目印が表示され、入力行がDOMからなくなり、下書き保存ボタンが非表示になったことを確認します。次に「下書き:N件」から一覧を開き、タイトル「申請状況」と一覧の読込完了を確認します。状態が「下書き」、申請名が「勤務実績申請」、申請期間がExcelの対象月の初日から末日までに一致する行が1件だけあることを確認します。該当行の「勤務実績申請」リンクで右側の詳細を表示し、新たに表示された「申請書入力」の非送信ボタンで入力画面を開きます。「下書き」は表示ラベルなのでクリックしません。「削除」は操作しません。期間は和暦または西暦の年・月・日を両端で照合します。件数の増加は成功条件に使いません。

開き直した入力画面でも対象年月を確認し、全処理対象日の勤務体系・事由・出退勤・休憩・実働を読み戻します。一致した場合だけ保存確認済みとなります。再入力や再保存は行いません。対象がない・重複する・別月や部分期間しかない・内容が古い場合は停止し、Excelはinputに残します。一覧への移動と再表示は同じページまたは設定したiframeで行われる想定です。別タブなどの場合は実DOM確認後に対応が必要です。

提供HTMLの一覧親行 `tr.js-tm-tableRow.js-cm-scrTbl__innerTr` を使います。状態は `data-columnindex="0"` 内のラベル、申請名と開くリンクは同1、期間は同2です。左右に分かれた内側の表を親行でまとめ、行番号や識別IDに依存しません。「申請書入力」は提供HTMLの `button.js-edit`、`data-actionlog-actiontype="申請書入力"`、`type="button"` を組み合わせて特定し、クリック前にも表示名と非送信ボタンであることを確認します。画像からCSSクラスやHTML階層は推測していません。実ページでも対象月の一意性と一覧・詳細・入力画面への自動移動を確認済みです。URL内の組織固有識別子、一覧の暗号化ID、画像内の企業名・氏名は設定・テストに保存していません。

互換用の `countAndReturn` 方式は、申請期間画面への遷移と件数のちょうど1件増加だけを確認します。新規作成専用であり、既存下書きの更新には使いません。`message` 方式は `saveSuccess` / `saveSuccessText` を使います。今回の設定は `reopenDraft` です。

利用者によるElementsの検索で、絞り込み後の親行と日付属性付きinputが月の日数に一致すること、出退勤・休憩の手動入力が別の入力欄をクリックした後も表示に残ることを確認しています。その後、専用Edgeへの読取専用接続で、非表示の同名タイトルを除外した画面識別・対象年月・全日付・各日の6項目の読取に成功しました。実際の勤怠値を診断ログや資料へ記載していません。確認日の表示値の見比べは `check-screen.bat` でも行えます。このモードは画面をクリックせず、設定やExcelを変更しません。

利用者の通しテストでは、入力画面の識別、全対象日の自動入力・入力値検証、保存後の申請期間画面への遷移まで確認されています。その後、下書き一覧と詳細への移動・保存済み内容の照合・Excelコピーの退避まで完了しました。年月表示の追加取得は不要です。テスト実行自体はverifiedを自動変更しません。実画面での照合完了と通常実行の利用に合わせ、現在の設定は `verified: true` に切り替え済みです。

保存後の一覧入口は、目印の表示より遅れて表示される可能性があるため、一意な表示要素を待ってから操作します。タイトル・読込完了表示・申請書入力ボタンも非表示のテンプレートを除外します。実画面で、申請書入力を押した直後に同名タイトルが一時的に複数表示されることを確認したため、重複を即時エラーにせず、一意になるまで読取だけを繰り返します。入力画面はタイトル・下書き保存ボタン・日付行・各読取項目が揃ってから年月と値を照合します。

画面遷移の待機上限は `transitionTimeoutMs`（本番設定60000ミリ秒）です。省略時は既存の `timeoutMs` を使います。通常の入力操作の待機上限は `timeoutMs` のままです。60秒間固定で待つのではなく、準備完了を検出して次へ進みます。実DOMで確認した全画面読み込み要素を `busy: ".js-cm-progressBase"` として設定に分離し、表示中は操作しません。遷移直後の初期化との競合を避けるため、一覧操作では `transitionStableMs: 1000` により、要素が一意で読み込み表示のない状態が1秒続いてからクリックします。重複や読み込みが解消しない場合は期限で停止し、ボタンを再クリックしません。

入口で確認されたtype未指定のbuttonには、フォームに属さないことを実行時に検証する専用ガードを使います。明示的なsubmitやフォーム送信は許可しません。タイムアウトでは停止箇所を、URLやHTMLを含めずに表示します。

保存後に停止した場合の `verify-draft.bat` は、申請期間画面から対象月の下書きを開き直し、全対象日を照合するだけです。再入力・再保存はせず、一致した場合のみExcelを退避します。出社日・有休日は保存時と同じ指定を使います。

実画面の構造・値の単位・保存成功条件を確認してから `verified: true` にします。ログインID、Cookie、HTML全体などを設定やログへ保存する必要はありません。

## 検証の境界

保存前の勤務日数・実働・休憩は、全対象行を読み戻してExcelと比較します。非対象行は変更しないため、月全体の表示合計ではなく今回処理対象の合計です。指定した有休日は各行の事由・勤務体系と、通常勤務時間が空欄またはゼロであることを検証します。未指定の有休件数は比較しません。

模擬テストでは申請ボタンにカウンタを設け、正常系・異常系ともゼロを検証しています。実画面への読取接続は実施済みです。実データでの入力・入力値検証と保存後の遷移は利用者の通しテストで確認されていますが、保存済み内容の照合とExcelコピーの退避も完了しています。
