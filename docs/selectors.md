# 実画面へのセレクタ設定

`src/browser/attendancePage.ts` にDOMの構造やCSSクラスを埋め込まず、`config/selectors.json` に分離しています。未設定の要素があるか `verified: false` の間は自動操作に進みません。以下は将来の実画面確認担当者向けの手順です。

## 確認する情報

1. 勤務実績申請のタイトルと下書き保存ボタンで対象ページを識別します。タイトルは入力対象ではありません。対象iframeの有無も確認します。
2. 日付行の親要素と日付セルを確認します。今回の画面には年月表示がないため、`periodSource: rowDates` と `period: null` を設定し、`dateEvidence` の属性から対象年月を取得します。全日付の年月・日付表示・重複・欠落を確認します。表示要素がある別画面では従来の `display` 方式も使えます。
3. 各行の勤務体系・事由・出退勤・休憩・実働を読み取る要素。`readMode: text` はセル本文、`value` はinput/selectの現在値、`attribute` は `readAttribute` で指定した属性を読みます。`emptyAttributes` が指定されている場合、すべて空文字であることを確認します。複数の事由を単一事由として上書きしません。
4. 入力欄と操作方式。ネイティブinputは `fill`、ネイティブselectは `select`。値は勤務体系・事由のコード、時刻は`09:00`、休憩は小数時間`1.00`です。selectのoption値がコードと一致することを確認してください。
5. 編集ダイアログがある場合は行内の `editButton`、画面内の `editor`、編集画面内の `applyButton` をすべて設定します。直接編集ならすべて `null`。行確定ボタンはsubmitではなく、最終申請に無関係なものであることを確認してください。
6. 今回は成功メッセージが出ず、申請期間画面へ戻り下書き件数が増えると確認できました。`saveMode: countAndReturn`、件数要素を `draftCount`、遷移先の目印を `returnMarker` に設定します。従来の成功メッセージ方式は `saveMode: message` と `saveSuccess` / `saveSuccessText` で引き続き利用できます。

保存ボタンは変更可能な自由セレクタではなく、role=button、正確な名前「下書き保存」で固定します。最終「申請」のセレクタや操作メソッドはありません。クリック共通ガードで「申請」を含む名前・タイトル・本文を拒否します。

## 設定のスコープ

| キー | 検索範囲 |
| --- | --- |
| `frame` | ページ。iframeセレクタ1つ。なければnull |
| `title`, `period`, `rows`, `editor`, `saveSuccess` | ページまたは対象iframe |
| `draftCount`, `returnMarker` | ページまたは対象iframe。遷移後も再検索 |
| `dateCell`, `fields.*.read`, `editButton` | 該当する日付行 |
| `dateEvidence.selector` | 日付行内。指定属性の年月日をExcelと照合（チェックボックスは読取のみ） |
| `fields.*.input`, `applyButton` | 編集ダイアログ、または直接編集時の日付行 |
| `fields.*.activate`, `fields.*.commit` | 編集ダイアログ、または日付行。編集開始セルと確定先 |
| `fields.*.hour`, `minute`, `dayType` | `fields.*.input` の分割入力コンテナ内 |
| custom方式の `option` | ページまたは対象iframe |
| custom方式の `clear` | 編集ダイアログまたは日付行 |

`rows` は全日付行にマッチさせ、`dateCell` を正規表現で照合して日付行を特定します。行番号やクリック座標は使いません。日付行・入力欄の重複や非表示は停止条件です。仮想スクロールで未表示行がDOMにない場合も推測で進めず停止します。必要ならDOM確認後にスクロール用アダプターを追加してください。

customドロップダウンでは `control: "custom"`、コード置換用 `option: "[data-code='{code}']"` のような実際に確認したセレクタ、空欄へ戻す `clear` を設定します。これは形式例であり、奉行にこの属性があるという意味ではありません。

`tests/fixtures/selectors.json` に完成した**模擬画面専用**設定があります。キーの参考としてだけ使用し、実サイトへコピーしないでください。複数iframe階層、候補検索で確定する複雑なUI、保存確認ダイアログなどは実DOM確認後にPage Objectのアダプターを拡張する必要があります。未対応方式をセレクタだけで対応可能とは扱いません。

## 提供HTMLから確認できた構造

日付の固定表と勤務入力の横スクロール表は別々ですが、`tr.js-cm-scrTbl__innerTr` が両方を含みます。この親行を日付セルで絞り、`data-labordate` の年月日も照合します。左右の表に同じ行IDがあるため、行ID・行番号に依存しません。実日付や行識別子は設定へ固定していません。

- 勤務体系・事由はセルを選択してコード入力欄を開く形式です。非編集時のコードは `data-code` / `data-code1`、編集中の値は `inputValue()` で取得します。両者が異なる場合は未確定の手入力として停止します。
- 出退勤は `splitTime` 方式です。`dayType` は当日1・翌日2、`hour` と `minute` を別々に入力します。例として25:30は翌日・01・30です。前日区分には対応しません。
- 休憩は `splitDecimal` 方式です。提供HTMLの `DecimalSys` に合わせ、1.50時間なら整数部1・小数部50を入力します。入力欄のラベルが「分」でも30へ変換しません。
- 各セルは `activate` で開き、入力後に `commit` の要素をクリックして編集欄が閉じたことを確認します。その後、既存の検証処理で全対象行を読み戻します。時刻・休憩のセルが実行開始前から編集中の場合は、利用者が確定または取り消してから実行してください。

利用者から、事由・出退勤・休憩は日付セルをクリックしても戻らず、別の入力欄をクリックすると元の表示に戻ると確認できました。このため、勤務体系の `commit` は事由セル、その他の項目は勤務体系セルとしています。移動先のコードは書き換えず、現在値と確定済み属性の一致を読み戻し時に確認します。模擬画面も日付クリックでは閉じない方式に変更しています。実サイトで変更した値の確定・属性への反映はまだ未検証です。翌日の時刻を非編集状態でどう表示するかも未確認であり、未知の表示は推測変換せず停止します。

## 件数増加と画面遷移による保存確認

保存前の下書き件数を読み、下書き保存を1回だけ押します。保存後は、申請期間の目印が表示され、入力行と下書き保存ボタンがDOMからなくなり、件数がちょうど1件増えた場合に成功とします。単に件数が1以上あることでは成功扱いにしません。件数不変・想定外の増加・遷移未確認では停止し、Excelはinputに残します。既存下書きの上書き保存は件数が変わらない可能性があり、その場合は自動成功判定の対象外です。

スクリーンショットで確認した「下書き:N件」「申請期間」の表示文字列を使うセレクタ候補を設定しています。画像からCSSクラスやHTML階層は推測していません。実ページで一意に取得できるかは未検証です。URL内の組織固有識別子や画像内の企業名は設定・テストに保存していません。

まだ必要な確認は、実ページでのタイトル・日付行・保存前後の件数と遷移先目印の検出（iframeの有無を含む）、入力後の表示値と属性への反映、小数時間入力の実際の結果です。年月表示の追加取得は不要です。`verified: false` はこれらの確認まで維持します。

実画面の構造・値の単位・保存成功条件を確認してから `verified: true` にします。ログインID、Cookie、HTML全体などを設定やログへ保存する必要はありません。

## 検証の境界

保存前の勤務日数・実働・休憩は、全対象行を読み戻してExcelと比較します。非対象行は変更しないため、月全体の表示合計ではなく今回処理対象の合計です。指定した有休日は各行の事由・勤務体系と、通常勤務時間が空欄またはゼロであることを検証します。未指定の有休件数は比較しません。

模擬テストでは申請ボタンにカウンタを設け、正常系・異常系ともゼロを検証しています。実画面への接続確認、実データでの入力、実サイトの下書き保存は今回実施していません。
